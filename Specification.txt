Tend local No-code review package
Prepared 13 October 2026. Production mode and local preparation plan approved.

Purpose
Combine conversation and meeting evidence for a verified fictional contact. Show what the owner owes, what the contact owes, meeting context and source coverage. A model proposes a commitment; the owner confirms it explicitly. The package never sends to a contact.

Current delivered scope
Ten inactive n8n JSON exports, including a fail-closed Telegram control template. Five read fictional source records over a local HTTP API: Gmail, Calendar, WhatsApp Personal, WhatsApp Business and a LinkedIn snapshot. Each invokes the normalization/storage sub-workflow through its embedded JSON. This avoids requiring publication of an imported sub-workflow in n8n 2.43.4.
The local API checks record schema, timestamps and verified identities. It writes a transaction to SQLite. Source record IDs, owner, account and source define uniqueness. The same text on two channels remains two pieces of evidence. Failed transactions do not advance the cursor. Evidence edits invalidate derived commitments; an invalidated item cannot be confirmed or drafted without a separate review. Automatic replacement or reinstatement of invalidated candidates is outside this local demo. Terminal done/cancelled states are retained separately from evidence validity. Revocation removes source text and redacts derived quotes/actions.
The AI extraction workflow uses native n8n Basic LLM Chain and Ollama Chat Model nodes with the real local qwen3:0.6b model. A record selector supports g1 (incoming) and g2 (outgoing); the runtime check executes both and verifies owed-to-me and owed-by-me. It receives only fictional evidence. n8n checks exact quote/action fields; the API repeats validation against persisted evidence and validates dates. Accepted new output is pending, never an active obligation. Extraction is deliberately restricted to a single complete direct English utterance starting with I will or I promise to. Quoted replies and multiline messages are rejected for review.
The assistant workflow checks fictional owner ID, user ID and private chat ID before retrieval. It branches on allowed commands, then calls the owner-scoped API. /prep, /status and /today read. /confirm explicitly sets a date. /draft returns a template preview only. /done and /cancel require an existing confirmed obligation; repeated identical transitions are idempotent. The fixture clock is fixed at 13 October 2026.
The retry workflow demonstrates a synthetic 429 with Retry-After: 1. It retries at one-second intervals, at most three attempts, then records recovery only on the third attempt. Each workflow run creates a separate scenario ID; stray runs do not shift its counter. A separately tested retry policy rejects delays beyond its budget. This is not proof of any real provider's retry behavior.

Data and AI boundaries
The API accepts only demo-owner records with fixture:// references and fixture/snapshot mode. Do not feed real exports into it. The fixed fictional IDs are not production authentication. Commands are guarded before retrieval; local diagnostic status and fixture/model inputs intentionally expose only fictional data. Host/origin checks and application/json POSTs prevent cross-site browser mutation. No real records are accepted. The API listens on 127.0.0.1. Docker Desktop reaches it at host.docker.internal.
A local-model connection configuration is shipped: only the host.docker.internal Ollama base URL, with no API key or personal account secret. No Telegram account, Google OAuth, WhatsApp provider or LinkedIn account is connected. The Ollama model runs locally. The only draft destination is the owner preview. Source text cannot select recipients or mutate state. Model output with extra fields is rejected.
Persistence is real local SQLite. The PostgreSQL schema was executed successfully in an isolated PostgreSQL16 container (eight tables and two indexes). It remains a future migration design, separate from the demonstrated SQLite adapter. The package does not claim that Postgres backs the current demo.

Private Telegram control and replay
The verified new project bot is @tend_adam_nocode_2026_bot. Its token has not been read, exported or used by this integration worker. Adam enters it directly into n8n's Telegram credential UI. The template does not import inbox history: it accepts short slash commands only, from both the exact owner user and exact allowlisted private chat.
The native Trigger checks Telegram's secret header. Native n8n derives that secret from the workflow and trigger node IDs, so a separate ignored deployment copy generates fresh random IDs and a fresh webhook path. Never publish this live copy. The public source template uses placeholders and remains inactive/fail-closed.
The proxy binds localhost:18769 and accepts only the exact generated POST webhook path with the exact secret header. It rejects editor/API routes. Enrollment mode adds only the matching signed test path. Stop enrollment before live activation. n8n editor binds localhost:5678; fixture API binds localhost:18767.
Telegram update_id must be a nonnegative safe integer. SQLite's telegram_updates ledger uses (channel_id, update_id), with the stable single-bot namespace tend-course-control. Command state and the replay record commit in one transaction. Repeat delivery stops before command processing or a new reply, even after reopening the database. Replacing the project bot requires a deliberate new channel namespace to prevent update-ID collisions.
Native Send returns only to the configured owner. Replies are readable, labeled Course demo • fictional data, escaped as HTML text, and capped below 3,900 UTF-16 units. Suggested model dates say proposed/unconfirmed; only due_date is a confirmed due date.
External sending and the subsequent send acknowledgement are not atomic with SQLite. If execution stops before Send, the reply can be lost; if Send succeeds and acknowledgement is lost, the ledger remains reply_pending and delivery is uncertain. Native webhook receipt also precedes workflow completion. No exactly-once Telegram delivery is claimed, and old update IDs are never automatically resent. Check the owner's private chat, inspect aggregate delivery counts locally, and send a fresh command to recover. Fresh confirm/done/cancel commands remain state-idempotent.
The PostgreSQL file remains the earlier future-design schema. Telegram replay persistence is implemented and tested in the actual SQLite store.
