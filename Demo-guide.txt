Tend review demo: six minutes

Before class
Run bun install, bun run build, then bun run verify. Docker Desktop and Ollama must be running. Ensure qwen3:0.6b is installed. Run bun run schema:check for the reproducible isolated SQL check. Run bun run integration for the actual clean import/execution test; it creates its own temporary instance and stops it afterward. Check evidence/runtime-checks.json. If it fails, use the failed log, repair the cause and rerun. Never claim an unrun check passed.
For live rehearsal run bun run start, then open http://127.0.0.1:18767. The API is fictional-only. Import fixtures/local-ollama.json with n8n import:credentials --input=fixtures/local-ollama.json (only a keyless local base URL). Then use n8n import:workflow --separate --input=workflows in an isolated local n8n instance. Read Review.html for exact commands. Do not import these fixed IDs into an existing unrelated n8n instance.

0:00-1:15: problem and architecture
“I want one evidence-backed view of a contact across messages and meetings. Each source keeps its identity, source link and coverage. An AI candidate stays pending until I confirm it.” Show Architecture.mmd or the diagram in Review.html. State that all seven records are fictional, five account connectors are not live, persistence is SQLite and the extraction model is local Ollama.

1:15-2:15: n8n source orchestration
Show one adapter: manual fixture trigger, HTTP read, Execute Sub-workflow. Show Normalize and Store: Code scope guard, HTTP transaction. Execute the five adapter workflows. Show seven persisted records. Replay Gmail; count stays seven. Source IDs define uniqueness. The forwarded LinkedIn copy remains separate evidence.

2:15-3:05: real local AI extraction
Execute TendReview07. Show native Basic LLM Chain and Ollama Chat Model, their request, quote validation and pending candidate. The model is not allowed to pick recipients, execute tools or close tasks. Show evidence from g1 and g2. Run 07 on g1, change the selector to g2 and run again. The selector chooses incoming versus outgoing evidence; both remain pending until confirmed. State that prompt behavior beyond the tested fixture is not proven; deterministic guards reject fabricated quotes/dates/extra fields.

3:05-4:15: private briefing and owner commands
Execute TendReview08 for /prep F17. Show Gmail, meeting and WhatsApp/LinkedIn references plus stale/snapshot coverage. Try “Riley Park” through the local command API: ambiguity requires an ID. Confirm the pending candidate explicitly with a date, view a draft preview and mark done. Replay /done; state does not change again. The demo sends nothing to a contact.

4:15-5:00: failures and recovery
Show the owner/private-chat guard; the group-chat test is rejected before retrieval. Show malformed date and injected-field tests. Execute TendReview09: first two local responses are synthetic429, third succeeds with bounded one-second retries. Describe live retries/authorization as untested connector work.

5:00-6:00: questions and limits
Be ready to explain source uniqueness, actor direction, why timestamps must be valid, why same names do not merge contacts, why pending differs from confirmed, and why a snapshot cannot establish ongoing sync. Identify each Code and If node. Explain where SQLite persists and how Postgres would replace it.
If asked whether the project is validated, say teacher validation and public link are pending. The 15 October cutoff requires completed review-ready work; the 22 October demo is separate. Do not say accounts are connected or that this package accesses all chats.

Fallback
If Docker/Ollama is unavailable, show the previously recorded evidence/runtime-checks.json, fixture data and tests. Call it recorded evidence, not a live execution. This fallback does not replace a required working class demo.

Secure Telegram setup handoff
1. Complete the n8n owner password setup directly at http://localhost:5678. Keep the editor local. Adam enters the new bot token directly into a Telegram credential named TendReviewTelegram; never paste it into chat, shell, source or public review.
2. Run bun run telegram:prepare once. It writes .scratch/live-telegram/workflow.json with private random workflow/trigger/webhook IDs, no token or owner IDs. Import this private file, not the public template. Select the credential on native Trigger and Send. Keep the workflow inactive while enrolling.
3. Start bun run telegram:proxy -- --enrollment. Only the exact signed production/test webhook routes are permitted. A temporary Cloudflare Quick Tunnel targets localhost:18769. Its HTTPS base URL must become n8n WEBHOOK_URL while preserving the existing data volume; restart only the owned service when no one is entering credentials. Never tunnel localhost:5678 or the fixture API.
4. For one controlled trigger test clear only its chat/user restrictions. Keep the Code allowlist placeholders unchanged and execution saving set to none. Adam deliberately sends /start with a one-time marker from the known signed-in account to the new bot. In the trigger output verify that known private update; read from.id and chat.id. Do not auto-claim the first visitor and do not use a third-party ID bot. Unconfigured Code stops before any Tend retrieval/reply.
5. Set both trigger restrictions and both Code allowlist constants from that verified owner update. Stop test listening. Restart proxy without --enrollment. Publish/activate only the privately configured workflow after review. Test owner /status, /prep F17, /today and /help through Telegram, then check duplicate-update and foreign/group rejection using synthetic local checks. Never send a test to another human/contact.
6. Keep public review artifacts separate. Never publish the live export, webhook path, owner IDs, token, n8n database/configuration or private runtime logs. A Quick Tunnel URL changes when restarted; keep the laptop and owned services running for a live demo. Refresh WEBHOOK_URL and webhook registration after a tunnel change. Public teacher review is a separate stable static page.

Delivery recovery
A duplicate Telegram update is durably ignored. A newly sent owner command has a new update ID. If a reply is absent or delivery acknowledgement is uncertain after a crash, inspect the private chat and send a fresh /status or the original state-idempotent command. Do not replay the old update ID or claim exactly-once external message delivery.
